# Mr.Shop — Example Conversations & Design Decisions

## Example Conversations

The conversations below show the full pipeline: Tier 1/2 classification, topic
switching, reference resolution, tool dispatch, and memory persistence across turns.
Turn traces are shown as they appear in the REPL after each reply.

> Replies shown are illustrative of the pipeline behaviour. In full LLM mode,
> the response text is generated by Ollama with full session context injected —
> natural language, not fixed templates. In degraded mode (no Ollama), the
> `template_reply` fallback produces the structured format shown below.

---

### 1 — Happy path (wardrobe → styling → purchase)

```
You: I just bought a navy blazer
Mr.Shop: Got it! I've added 'navy blazer' to your wardrobe. You now have 1 item.

turn_trace: {
  intent_source: rule, confidence: 1.0, tools_invoked: [wardrobe_upload],
  topic_switch: False, latency_ms: {tier1_ms: 0.3, tool_ms: 0.1, total_ms: 1.2}
}

You: What goes well with it?
Mr.Shop: Your navy blazer pairs beautifully with slim chinos and loafers for a smart
casual look, or dark jeans and white sneakers if you want something more relaxed.

turn_trace: {
  intent_source: rule, confidence: 1.0, tools_invoked: [styling_advice],
  topic_switch: True, latency_ms: {tier1_ms: 0.4, tool_ms: 0.1, total_ms: 2800}
}

You: I'll take the chinos — buy them
Mr.Shop: Purchase started for 'chinos' at $99.99. Your cart now has 1 item.

turn_trace: {
  intent_source: rule, confidence: 1.0, tools_invoked: [purchase],
  topic_switch: True, latency_ms: {tier1_ms: 0.3, tool_ms: 0.1, total_ms: 2400}
}
```

**What this shows:** Tier 1 handles all three turns instantly (confidence 1.0).
`topic_switch: True` fires on turns 2 and 3 — the old topic is parked in
`topic_history` but wardrobe items survive so styling advice on turn 2 can
reference the navy blazer added in turn 1. The LLM generates the reply for turns
2 and 3 with full session context (wardrobe, gender, budget, preferences).

### 2 — Reference resolution

```
You: I own a leather jacket and some white sneakers
Mr.Shop: Added your leather jacket to your wardrobe!

You: Also add the sneakers
Mr.Shop: Done — white sneakers are in your wardrobe. You now have 2 items.

You: Can I buy that jacket?
Mr.Shop: Purchase started for 'leather jacket' at $99.99. Your cart now has 1 item.

turn_trace: {
  intent_source: rule, confidence: 1.0, tools_invoked: [purchase],
  topic_switch: True, resolver_source: llm, latency_ms: {tier1_ms: 0.4, total_ms: 3100}
}
```

**What this shows:** "that jacket" is resolved by `llm_resolve` — it checks the
wardrobe, finds "leather jacket" as the obvious match, and returns it. The assumption
disclaimer is suppressed because the source is `"llm"`, not `"heuristic:last_mentioned"`.

---

### 3 — Heuristic fallback with transparent assumption

```
You: Show me styling ideas for the weekend
Mr.Shop: Here are some outfit ideas: ...

You: Can I purchase it?
Mr.Shop: Purchase started for 'leather jacket' at $99.99. Your cart now has 1 item.
         (I'm assuming you mean 'leather jacket' — let me know if you meant something else.)

turn_trace: {
  intent_source: rule, confidence: 1.0, tools_invoked: [purchase],
  topic_switch: True, resolver_source: heuristic:last_mentioned
}
```

**What this shows:** "it" has no explicit antecedent in this turn. Heuristic
resolver falls back to `last_mentioned_item` from memory and surfaces the assumption
in the reply. With Ollama active, `llm_resolve` would extract the correct referent
from context instead.

### 4 — Mid-conversation topic pivot (styling → booking)

```
You: What can I wear to a job interview?
Mr.Shop: For a job interview, I'd suggest your navy blazer with tailored trousers...

You: Actually, book me a stylist session for Thursday
Mr.Shop: Booked! Stylist Alex will see you Thursday. Confirmation: MRSHOP-48210.

turn_trace: {
  intent_source: rule, confidence: 1.0, tools_invoked: [booking],
  topic_switch: True, latency_ms: {tier1_ms: 0.5, total_ms: 2600}
}
```

**What this shows:** User pivots from styling to booking mid-thread.
`switch_topic` parks `styling_advice` in `topic_history`, sets `booking` as
current. Wardrobe items and preferences are unaffected.

### 5 — Tier 2 embedding path

```
You: I've been thinking I need something for rainy days outdoors

turn_trace: {
  intent_source: embedding, confidence: 0.41, tools_invoked: [styling_advice],
  latency_ms: {tier1_ms: 0.4, tier2_ms: 87.3, total_ms: 2950}
}
```

**What this shows:** No keyword/regex rule fires (Tier 1 returns `None`).
all-MiniLM-L6-v2 embeds the query and scores it against the intent taxonomy;
`styling_advice` wins at 0.41 (above the 0.33 threshold). `intent_source: embedding`
in the trace makes the routing decision fully auditable.

### 6 — Greeting and side-channel extraction

```
You: Hey! I'm a woman and I love minimalist style
Mr.Shop: Hey! Great to meet you. I can help with your wardrobe, styling advice,
         purchases, or booking a stylist — what would you like to do?

turn_trace: {
  intent_source: clarify, confidence: 0.19, tools_invoked: [],
  resolver_source: none, topic_switch: False
}

[session: gender=female, preferences.style=minimalist]
```

**What this shows:** Tier 2 scores everything below 0.33 so intent is `unclear`.
The resolver is skipped entirely for `unclear` (no item to resolve, and running it
on greetings caused junk words to pollute `last_mentioned_item`). The LLM responds
naturally. Meanwhile, the side-channel extraction runs independently — gender and
style preference are extracted from the same utterance and stored in session memory
for all future turns.

### 7 — Session persistence across restarts

```
# First session
You: I just got a navy blazer
Mr.Shop: Added navy blazer to your wardrobe!
You: quit

# Second session (new process)
[storage] Session restored from Redis (user=local, wardrobe=1 item(s))
Ready!

You: show my wardrobe
Mr.Shop: You have 1 item: navy blazer.
```

**What this shows:** Redis persists the full session dict (including wardrobe,
gender, budget, preferences) after every turn. On the next run, `load_session`
restores it. The user picks up exactly where they left off.

## Design Decisions

### 1. Three-Tier Classification

**Decision:** Sequential tiers — keyword/regex (instant) → embedding similarity
(~90ms CPU) → local LLM (optional, async).

**Why not one LLM call for everything?**

An LLM call for every turn adds 1–5s latency and requires GPU infrastructure.
~80% of fashion-app utterances are patterned enough for Tier 1 ("I just bought",
"what goes with", "book a stylist"). Tiers 1–2 together handle the full load with
no GPU and sub-100ms latency; the LLM is additive for reference resolution and
response generation.

The `intent_source` field in every `turn_trace` keeps the routing decision
auditable. If Tier 1 is over-firing on a new intent, a single regex change fixes
it without touching anything downstream.

**Threshold tuning:** `DEFAULT_THRESHOLD = 0.33` for Tier 2 was set empirically
by running the classifier against 83 test cases. The threshold is overridable via
`TIER2_THRESHOLD` env var for per-deployment tuning without code changes.

---

### 2. Tool Registry — One File Per Intent

**Decision:** `mrshop/tools/registry.py` defines a `ToolDefinition` dataclass.
Each tool file calls `register()` at the bottom with all its metadata: Tier 1
patterns, Tier 2 taxonomy sentences, LLM reply instruction, dispatch priority,
resolver strategy, and the `run` callable.

```python
register(ToolDefinition(
    intent="size_check",
    tier1_priority=35,
    tier1_patterns=[r"\bwhat size\b", r"\bdo you have .{0,20} in\b"],
    tier2_examples=["What size is this item?", "Do you have this in medium?"],
    llm_instruction="Confirm size and availability in 1–2 sentences.",
    run=lambda utterance, resolved_item, state: size_check(resolved_item or utterance, state),
))
```

**Why this matters:** Before the registry, adding a new intent required changes in
four places (tier1, tier2, orchestrator dispatch, reply instructions). Now it
requires one. The classifiers and orchestrator read from the registry lazily —
tool files are auto-discovered via `pkgutil.iter_modules` so even the import list
doesn't need updating.

---

### 3. Swappable Resolver and Reply Generator via Dependency Injection

**Decision:** Both the resolver and reply generator are async callables injected
into `Orchestrator.__init__`. `config.bootstrap()` is the only place that reads
`LLM_ENABLED`.

```python
ResolverFn = Callable[[str, dict], Coroutine[..., tuple[str|None, str]]]
ReplyFn    = Callable[[str, str, dict, str|None, str, dict], Coroutine[..., str]]

# Orchestrator never sees LLM_ENABLED:
orch = Orchestrator(resolve_reference=resolver, generate_reply=reply_fn, state=state)

# bootstrap() selects once at startup:
resolver, reply_fn = heuristic_resolve, template_reply   # or llm pair
```

**Why this matters:** Swapping from Ollama to any other provider (OpenAI, Gemini,
a fine-tuned model) means implementing one new async function with the matching
signature. Tests inject `(heuristic_resolve, template_reply)` in two lines without
patching environment variables.

---

### 4. LLM as the Response Voice

**Decision:** The LLM (`llm_reply`) generates all replies — not just resolves
references. Classifiers and tools provide structured context; the LLM synthesises
the final natural-language response with full session state injected into the prompt.

**Why:** Template strings produced canned responses that broke for anything outside
the happy path. "Hello" routed to `unclear` and got a generic bulleted list.
With the LLM as the response layer, every intent — including `unclear` greetings —
gets a coherent, context-aware reply. The `template_reply` fallback remains for
degraded mode.

**Streaming:** `llm_reply` uses Ollama's `stream=True` and calls an `on_token`
callback per chunk, giving the terminal typewriter output. The orchestrator threads
`on_token` through to the generator; the REPL wires it to a `print + sleep` function.

---

### 5. Side-Channel Extraction

**Decision:** On every turn, three independent regex passes extract gender, budget,
and style/colour preferences from the raw utterance — regardless of the classified
intent.

```python
# MEMORY_UPDATE phase in orchestrator.handle_turn():
gender = _extract_gender(utterance)          # "I'm a woman" → female
budget = _extract_budget(utterance)          # "my budget is $200" → 200.0
style, colors = _extract_preferences(utterance)  # "I love navy and black" → colors
```

**Why:** These signals appear mid-conversation without being the primary intent.
A user saying "I prefer earth tones, what goes with dark jeans?" is asking for
styling advice — but the colour preference should be captured too. All extracted
signals flow into the LLM prompt on every subsequent turn.

---

### 6. Memory Helpers, Not Raw Dict Access

**Decision:** All layers call typed helpers (`session.add_wardrobe_item`,
`session.add_to_cart`, `session.set_budget`) rather than mutating the dict directly.

```python
session.update(state, unknown_key="value")
# → KeyError: Unknown session state key: 'unknown_key'
```

**Why:** The schema is the source of truth. Any attempt to invent a new top-level
field fails loudly at the line that introduces it. The `cart` field was previously
added ad-hoc in `purchase.py` with `state["cart"] = []`, bypassing this guard
entirely — it has since been added to `new_session()` and accessed through
`add_to_cart()`.

`switch_topic` explicitly does *not* wipe adjacent state. Wardrobe, cart, budget,
gender, and preferences survive topic changes.

---

### 7. Redis Session Persistence

**Decision:** `mrshop/storage/redis_store.py` saves the full session dict to Redis
as JSON after every turn, keyed by `mrshop:session:{user_id}` with a configurable
TTL (default 24 hours).

```
mrshop:session:local  →  {"wardrobe_items": ["navy blazer"], "gender": "male", ...}
```

**Why Redis over a file:** Namespacing by `MRSHOP_USER_ID` makes multi-user support
trivial — the same Redis instance serves any number of users with no code changes.
TTL-based expiry cleans up stale sessions automatically with no cron job. The
session dict is intentionally flat and serialisable (strings, lists, None only) so
`json.dumps / json.loads` is sufficient.

**Graceful degradation:** `get_client()` returns `None` if Redis is unreachable.
The REPL falls back to in-memory silently, matching the Ollama fallback pattern.

---

### 8. Resolver Skip for `unclear` Intent

**Decision:** When intent is `unclear`, reference resolution is skipped entirely
and `(None, "none")` is returned directly.

**Why:** Running the resolver on greetings like "Hello" caused the LLM to extract
"hello" as a clothing item reference, setting `last_mentioned_item = "hello"`. This
then polluted subsequent turns — "style it" would incorrectly try to style "hello".
`unclear` turns have no tool call and no item to resolve, so there is nothing to
extract. Skipping is both correct and faster.

---

### 9. Degraded Mode as First-Class Design

**Decision:** Every external dependency has a silent fallback:

| Situation | Behaviour |
|-----------|-----------|
| Ollama unreachable at startup | `(heuristic_resolve, template_reply)` selected |
| Ollama fails mid-session | `llm_resolve` / `llm_reply` catch exception, fall through |
| Redis unreachable | In-memory session, no persistence, no crash |
| LLM returns empty / "none" | Falls through to heuristic / template |

**Why:** The system must be runnable without GPU, without a cloud account, and
without a Redis server. Each layer degrades independently — Redis can be down while
Ollama is up, or vice versa. The user sees a one-line status message; nothing else
changes.

---

### 10. Async Boundaries

**Decision:** `Orchestrator.handle_turn` is `async def`. Tiers 1–2 are sync.
Resolver and reply generator are `await`ed because both can make real async HTTP
calls to Ollama.

**Why not async all the way down?** Tiers 1 and 2 are CPU-bound and complete in
<100ms — there is no I/O to overlap. The boundary sits exactly where it needs to.

`asyncio.run(orch.handle_turn(raw))` per turn in the REPL is the simplest correct
integration. An API server (FastAPI, Starlette) would call
`await orch.handle_turn(raw)` inside a route handler — no orchestrator changes needed.

---

### 11. Tools as Pure Functions

**Decision:** Each tool (`wardrobe_upload`, `styling_advice`, `purchase`, `booking`)
is a plain function: reads/writes one shared `state` dict via memory helpers, returns
a plain dict. No HTTP, no side effects beyond the state mutation.

**Why this maps to LLM function-calling:** The return shape maps directly onto what
an LLM function-call result looks like. Swapping the orchestrator for an LLM-native
agent (Claude tool-use, OpenAI function-calling) would mean wiring the same function
signatures into the model's tool registry — implementations are untouched.

---

### 12. Turn Trace for Observability

**Decision:** Every `handle_turn` call returns a `(reply, turn_trace)` pair.

```python
{
  "turn_id": 3,
  "intent_source": "rule",       # rule | embedding | clarify
  "confidence": 1.0,
  "resolver_source": "llm",      # llm | explicit | heuristic:last_mentioned | none
  "tools_invoked": ["purchase"],
  "topic_switch": True,
  "latency_ms": {
    "tier1_ms": 0.3,
    "tool_ms": 0.1,
    "total_ms": 2847.3
  }
}
```

`intent_source` tells you which tier fired. `resolver_source` tells you how the
item reference was resolved. Per-component latencies let you diagnose whether
Tier 2 or Ollama is the bottleneck. This is enough signal to catch classification
regressions and latency spikes without a metrics service.
